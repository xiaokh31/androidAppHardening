# 威胁模型

## 1. 目标与结论

本项目保护 APK 中业务 DEX 的静态机密性和启动完整性，并提高运行时导出、调试、Hook 和篡改成本。它不能在完全由攻击者控制的 Android 设备上提供不可提取的客户端秘密，也不能绝对阻止业务 DEX 在执行期间被观察。

安全主张限定为：

- 分发包中不再直接包含原业务 DEX 明文条目；
- DEX 容器使用标准认证加密，离线篡改可被检测；
- Runtime 在业务类加载前验证安装 signer 和容器完整性；
- 密钥与明文的内存和磁盘暴露面被压缩；
- 风险信号可提高自动化分析成本，但不会被描述为绝对防御。

## 2. 资产

| 资产 | 保护目标 |
| --- | --- |
| 输入 APK | Host 处理全过程保持字节级不变 |
| 业务 DEX | 静态机密性、加载前完整性、最短明文生命周期 |
| 内容加密密钥 | 不出现在日志、报告、磁盘明文或单一易提取位置 |
| signer 身份策略 | 防止输出被其他证书重签后正常运行 |
| Manifest 启动语义 | 保持原 Application、Factory、Provider 行为 |
| Host 与 Runtime 发布物 | 来源可追溯、构建可复现、未被供应链替换 |
| 诊断与报告 | 可审计且不泄露敏感材料或用户目录 |

## 3. 参与者与信任假设

### 3.1 可信

- APK 拥有者控制输入用途及仓库外签名流程。
- 经审查并锁定的项目源码、构建工具和依赖。
- 未被攻击者控制的 CI 发布环境。

### 3.2 不可信

- 输入 APK 的 ZIP、AXML、DEX、资源和签名结构。
- Host 文件系统中的并发进程和可预测临时路径。
- 输出 APK 在签名与分发链路中的存储介质。
- Android 用户空间环境、调试器、Hook 框架、模拟器与具有 root 权限的攻击者。
- 容器内所有长度、偏移、计数、字符串和密文。

### 3.3 必要假设

- 使用方以输入 APK 的同一当前签名证书在产品外签署输出。
- Android 平台的公开签名 API、AES-GCM 实现和系统 ClassLoader 行为符合其公开合同。
- 攻击者若具有内核级或进程完全控制能力，最终可以观察正在使用的类或密钥；项目只增加成本。

## 4. 信任边界

### TB-1 Host 参数与文件系统

用户路径进入 CLI。必须规范化路径、拒绝输入输出同文件、避免符号链接或重解析点造成覆盖，并使用权限受限的随机临时目录。

### TB-2 APK Parser

不可信 ZIP/AXML/签名数据进入解析器。所有计数和偏移均需上限、溢出检查和完整消费校验。

### TB-3 Host 到输出 APK

Host 生成的 bootstrap、容器与元数据汇合。输出验证器必须独立重读最终文件，而不是复用构建器的内存模型。

### TB-4 外部签名流程

产品输出未签名 APK，签名由使用方完成。产品不跨越该边界获取凭据。Runtime 只验证安装后公开证书身份。

### TB-5 Android Runtime

实测安装 signer、Framework `ApplicationInfo`、当前 APK 中的 ConfigV2/AHDC 固定条目和环境信号进入 Runtime。ConfigV2 在完整 digest 被已认证 AHDC header 绑定前仍不可信；业务代码和原 Factory 只能在强完整性校验通过后加载。

## 5. 威胁与控制

| ID | 威胁 | 主要控制 | 残余风险 |
| --- | --- | --- | --- |
| T-01 | ZIP 路径穿越覆盖 Host 文件 | 不直接按条目路径解压；规范化、根目录约束、随机临时目录 | Host 或依赖实现漏洞 |
| T-02 | 压缩炸弹或超大计数耗尽资源 | 条目数、单条目、总解压大小、压缩比和时间上限 | 合法大型 APK 可能被保守拒绝 |
| T-03 | 整数溢出绕过容器边界 | 固定宽度无符号解析、checked arithmetic、消费长度一致性 | Native parser 缺陷 |
| T-04 | 重打包后仍携带失效签名材料 | 显式移除 META-INF 签名文件与 APK Signing Block，验证为未签名 | 非标准工具可能误解状态 |
| T-05 | 攻击者以其他证书重签 | 嵌入输入当前 signer SHA-256，运行时在业务加载前验证 | 攻击者修改并重新构建 Runtime |
| T-06 | 密文、record 或 chunk 索引被篡改 | HeaderV2 table manifest MAC、每个 64 KiB chunk 的 AES-256-GCM、严格版本/长度/完整消费；tag 成功后才进入 inflater | 拒绝服务仍然可能 |
| T-07 | 静态恢复内容密钥 | 每包随机密钥、分片、Native/Java 分离、signer 绑定 | 离线 Runtime 必须能恢复密钥，确定性逆向最终可行 |
| T-08 | 运行时抓取明文 DEX | 内存 ClassLoader、短生命周期缓冲、清零、避免落盘和副本 | 进程控制、Hook 或内核能力可观察明文 |
| T-09 | 调试或 Hook 绕过检查 | 多源信号、校验分散、策略版本化、关键结果交叉验证 | 高权限攻击者可以补丁 Runtime |
| T-10 | 环境误报阻止合法用户 | 低置信信号只触发 `degrade`，矩阵与真实设备测试 | 新设备或 ROM 仍可能误报 |
| T-11 | 自定义组件初始化次序改变 | API 29 公开 ClassLoader hook、原 Factory 委托、启动 fixture | 特殊框架不在支持范围 |
| T-12 | 临时文件、未发布映射或日志泄露 | 不落盘明文 DEX、handle 发布前事务 owner 对 completed/partial DEX 清零并 unmap、最小日志、报告字段白名单 | 崩溃转储或恶意 Host 进程 |
| T-13 | 依赖或 CI Action 被替换 | 固定版本/commit、校验和、依赖验证、SBOM、许可证审查 | 上游已固定版本本身可能含漏洞 |
| T-14 | 输入被处理器意外覆盖 | 双哈希、只读句柄、独立输出、原子发布 | Host 文件系统或用户并发替换 |
| T-15 | Manifest 过度修改引入后门或兼容问题 | 只替换 `appComponentFactory`、转换后语义 diff、fixture | 未覆盖的厂商扩展 |
| T-16 | 未认证启动配置注入 Factory 或策略 | 固定 sourceDir 条目、ConfigV2 严格解析、CEK/manifest MAC/完整 config digest 绑定后才消费 | 攻击者 patch Runtime |

## 6. 滥用情形

### 6.1 恶意 APK 作为输入

攻击者构造畸形 ZIP、AXML 或签名结构攻击 Host。所有输入路径都必须在无写出副作用的情况下被拒绝；解析器进入模糊测试语料库。

### 6.2 被替换的输出

攻击者在外部签名前替换未签名输出。使用方应核对报告中的输出 SHA-256，并在签名后执行结构、签名和设备回归。发布流程不得只按文件名信任产物。

### 6.3 不同证书重签

攻击者重签加固 APK。Android 可能允许作为不同应用安装，但 Runtime 必须在加载业务 DEX 前发现 signer 不匹配并拒绝。

### 6.4 Runtime 补丁

攻击者修改 Runtime 以跳过校验并重新签名。这属于本地离线模型的残余风险。项目通过完整性耦合、signer 绑定和多处交叉验证提高工作量，但不声称不可绕过。

## 7. 不属于安全主张

- 防止拥有源代码、构建环境或签名权限的内部人员提取业务逻辑。
- 在 root、内核控制或硬件调试能力下保守任何永久客户端秘密。
- 阻止屏幕抓取、业务 API 仿冒或服务端滥用。
- 保护 Flutter、Unity、React Native、热修复或已有壳的特殊字节码/Runtime。
- 保证输出 APK 体积更小。
- 通过 ABI 注入实现原应用 Native 代码的跨架构转换。

## 8. 安全测试要求

- ZIP、AXML、container 和报告 parser 均执行覆盖引导模糊测试。
- 每个边界字段具有截断、溢出、重复、乱序和未知版本用例。
- 修改 signer digest、HeaderV2、record/chunk table、nonce prefix/ordinal、ciphertext、tag、DEX 次序和 ConfigV2 任一字段时均应在业务代码前失败；受影响 chunk 的认证失败不得向 inflater 提交该 chunk。
- 日志和报告接受敏感词、DEX magic 与路径泄露扫描。
- 处理成功、失败和强制终止后检查临时目录与明文残留。
- 安全敏感变更由未参与实现的复核者给出书面结论。

## 9. 维护

当新增输入类型、Android API、ABI、容器版本、风险信号、第三方解析器或密钥恢复机制时，必须在实现前更新本威胁模型和相应 ADR。每个发布里程碑重新确认资产、信任边界、残余风险和产品安全表述。
