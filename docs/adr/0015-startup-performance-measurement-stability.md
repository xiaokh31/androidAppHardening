# ADR 0015: Startup performance and measurement-stability boundary

## Status

Proposed

## Context

M3-05 produced two complete API 36 x86_64 reports around a tool-only validator correction. The first report passed the fixed startup budgets. The second report recorded a `kotlin-multidex` `processToApplicationOnCreateMs` P50 delta of 331 ms against the fixed 300 ms budget, and six P50/P95 summaries differed by more than the fixed 10% repeatability limit. Both reports completed the production Guard, authenticated container, Release/R8 startup, LOW observation, isolated HIGH evidence and cleanup.

The current orchestration measures every baseline launch as one full batch and then every protected launch as a second full batch. Its repeatability tool compares protected absolute summaries from separate runs. This makes execution order, hosted-runner drift and emulator age indistinguishable from protected-startup cost. The two retained reports are therefore valid failure evidence, but they do not locate the cost inside production Runtime and do not authorize weakening a security control or opportunistically optimizing an unproven stage.

## Decision

M3-05 must replace the ambiguous comparison with exactly two complementary campaigns inside one API 36 KVM job, on one exact commit and one emulator boot.

1. Campaign `A` uses fixture order `java-single-dex`, `kotlin-multidex`, `jni-four-abi`; for every fixture it measures `baseline_then_protected`.
2. Campaign `B` reverses both axes: fixture order `jni-four-abi`, `kotlin-multidex`, `java-single-dex`; for every fixture it measures `protected_then_baseline`.
3. Each campaign and mode retains five warmups and thirty measured cold starts. Every sample remains force-stopped, finite and retained. An incomplete, malformed or timed-out sample fails that campaign; no outlier deletion, replacement sample or silent retry is permitted.
4. Both campaigns use byte-identical APK inputs, the same toolchain, the same API 36 system image, the same emulator process and the same environment fingerprint. A report records only non-sensitive identifiers and SHA-256 values; it never records a device serial or user path.
5. Each campaign independently applies the unchanged M3-05 P50/P95 startup and memory budgets. Both campaigns must pass every budget.
6. Repeatability compares `baselineP50`, `baselineP95`, `protectedP50`, `protectedP95`, `deltaP50` and `deltaP95` for every fixture and observed Android metric. Variation is `abs(A-B) / max(1, min(abs(A), abs(B)))`; the unchanged limit is `0.10`. Every comparison must pass.
7. Acceptance uses the first and only A/B pair generated by the exact-head job. A third campaign, another emulator boot, another job or a different commit cannot replace a failed result.

The aggregate evidence file is `benchmark-repeatability.json`. It binds the exact head, environment fingerprint, boot identifier hash prefix, shared artifact-manifest SHA-256, campaign order, report hashes, warmup/sample counts, all ninety comparison rows, budget status, repeatability status and cleanup status. The formal validator is:

```text
node tools/governance/verify-m3-08-startup-stability-contract.mjs \
  --report <benchmark-repeatability.json> \
  --campaign-a <campaign-a-benchmark-results.json> \
  --campaign-b <campaign-b-benchmark-results.json> \
  --expected-head <GITHUB_SHA> \
  --expected-run-id <GITHUB_RUN_ID> \
  --expected-job-id <GITHUB_JOB> \
  --expected-run-attempt <GITHUB_RUN_ATTEMPT> \
  --expected-environment <environment-id> \
  --expected-boot-hash <boot-id-sha256-prefix> \
  --artifact-manifest <benchmark-artifact-manifest.json> \
  --artifact-root <canonical-apk-directory>
```

The validator reads both retained campaign reports, computes their SHA-256 values, invokes the M3-07 report validator, recomputes all baseline/protected P50/P95 and deltas from the raw samples, and applies the fixed budgets. The canonical JSON artifact manifest binds the executing head/run/job/attempt/environment/boot, campaign A/B identities and exact fixture/mode order, the two distinct report hashes, and six uniquely identified baseline/protected APK SHA-256 values. The validator parses that manifest, matches it to explicit values supplied by the executing job, hashes each canonical APK under `--artifact-root`, and then hashes the manifest bytes for the aggregate binding. Self-reported aggregate booleans, hashes and summary values are never sufficient evidence; identical report bytes under different paths, historical-job manifests and mismatched APK bytes are rejected.

M3-08 is a governance-only prerequisite. It does not change Runtime, Host, fixture or benchmark implementation. After M3-08 merges, M3-05 may implement this measurement-only correction in PR #63 and run one replacement API 36 job. If that same-head A/B result is stable but still exceeds a fixed budget, the failure is eligible for a separate Runtime optimization task with its own ADR, implementation, regression tests and independent security review. M3-05 itself may not change production Runtime.

## Consequences

- Order bias and host/emulator drift become explicit rather than being conflated with protected startup cost.
- The release budgets, ten-percent limit, warmup count, sample count and all security controls remain unchanged.
- The replacement costs one API 36 KVM job containing two campaigns, not an unbounded rerun loop.
- Existing reports remain retained as diagnostic failure evidence but cannot satisfy the new exact-head acceptance contract.
- ARM validation remains blocked until the API 36 A/B job passes; it then runs exactly once under the unchanged M3-05 contract.

## Rejected Alternatives

- Raise the 300/500 ms budgets or the 10% limit: hides a release failure instead of explaining it.
- Reduce samples, discard outliers or keep rerunning until green: enables result selection and destroys reproducibility.
- Compare reports from different commits, jobs or emulator boots: cannot distinguish code changes from environment changes.
- Disable signer, AEAD, authenticated metadata, Guard ordering, memory controls, four-ABI packaging or cleanup: changes the protected product being measured.
- Add a production benchmark flag, timing hook, environment variable, manifest control or public/package-private API: creates an attacker-influenced or distributable test surface.
- Optimize production Runtime before phase evidence is stable: changes a security-sensitive path without a demonstrated cause.

## Security Impact

No product behavior or security decision changes. Signer verification, authenticated container parsing, metadata binding, class-loader publication ordering, LOW/HIGH memory controls, read-only and `DONTDUMP` mappings, cleanup and four-ABI behavior remain active. A future production optimization is not authorized by this ADR; it requires a separate task after stable evidence identifies a production-stage budget failure.

## Compatibility Impact

No wire format, API, ABI, minimum SDK, supported application class or compatibility claim changes. The protocol only changes how M3-05 schedules and compares test executions on its already fixed API 36 x86_64 reference environment.

## Verification

- Governance requires ADR 0015, M3-08, M3-05, TEST_STRATEGY and the task dependency graph to agree on the two-campaign contract.
- The M3-08 validator rejects production/runtime changes in this task diff.
- Synthetic aggregate-report mutations reject wrong order, a third campaign, changed head/environment/artifacts/boot, changed warmups or sample counts, missing/duplicate comparisons, relaxed limits, incorrect arithmetic, failed budgets and failed cleanup.
- Campaign-source mutations prove report SHA-256 binding, M3-07 validation, raw-sample percentile/delta/budget recomputation, positive and negative delta arithmetic, and the exact 10% boundary. Manifest mutations reject reused report bytes, historical job identity, wrong order and missing/duplicate APK identities. Recursive string scanning rejects Windows drive, UNC, macOS and Unix absolute or user-home paths plus device-serial fields.
- Independent read-only security review must return P0/P1/P2 all zero before M3-08 merges.
